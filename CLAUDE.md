# NEET-PG — project rules

Read this before adding or changing anything. These rules apply to every module in every subject, whoever writes it
(you or Claude). Each subject folder may also have its own `CLAUDE.md`; read that too. The rules follow the sister
project `jee-materials`, adapted for medicine.

## Purpose

- Revision for NEET-PG that makes the MBBS syllabus **visible**: anatomy you can turn in 3D, processes you can step
  through, findings you can compare. Not a PDF of one-liners.
- Audience: an MBBS graduate preparing for NEET-PG.
- **Learning material only on the module pages.** Quizzes and practice questions live separately (`practice/`, not
  linked yet); keep any that are written there, never on a learning page.
- **Anatomy is assembled.** The Anatomy page is the whole body in 3D with a filter per system; tapping a part opens its
  detailed page. Each region is built part by part (skull, then vertebrae, thorax, upper limbs, lower limbs…), then
  added to the assembled body. The same for each later system (muscles, vessels, nerves, organs).

## Syllabus

- NEET-PG has no syllabus of its own; NBEMS says questions come from the MBBS curriculum. The checklist is the NMC
  *Competency Based Medical Education Curriculum 2024*: root `SYLLABUS.md` + `<subject>/SYLLABUS.md`, every NMC topic and
  competency with its code (generated by `tools/syllabus/`).
- Before building a module, list what it will cover under the matching NMC competencies. After building, tick them in
  `<subject>/SYLLABUS.md` with the module name (`[x]` covered, `[~]` partly). Don't regenerate the SYLLABUS files once
  ticking has started (it would wipe the ticks).

## Repository layout

```
index.html                  hub: links to each subject
SYLLABUS.md                 NMC topic list: index
<subject>/                  anatomy/, physiology/, … (NMC subject names, lowercase-kebab-case)
  index.html                numbered list of that subject's modules
  SYLLABUS.md               NMC checklist for the subject
  CLAUDE.md                 subject-specific rules (when there are any)
  DATA-SOURCES.md           sources and verification log for that subject
  <branch>/<module>.html    one self-contained page per module
source/                     the original Revision Hub page (raw material, kept out of git)
tools/                      generators: syllabus/, bones/
```

Create a subject's `index.html` only when its first module is written. File names are lowercase-kebab-case.
Anatomy branches follow the NMC regions: `upper-limb/`, `lower-limb/`, `thorax/`, `head-neck/`, `back/` (vertebral column), `abdomen-pelvis/`,
`neuroanatomy/`, `histology/`, `embryology/`, `genetics/`, `general/`.

## Content rules (non-negotiable)

1. **No unverified data, two sources.** Every fact must be checked **before** it goes on a page, in two independent
   sources where at all possible. The owner cannot spot medical errors by eye, so this is the only safeguard. Sources
   we can legally read: Gray's *Anatomy* 20th ed. (1918, public domain; text via the Internet Archive copy of
   bartleby.com/107), Wikipedia (CC BY-SA; check its citations — much of its anatomy text is copied from Gray 1918, so
   it is not an independent second source for those sentences), StatPearls / NCBI Bookshelf, official guidelines,
   peer-reviewed papers. Never enter facts from memory. Never use pirated textbooks. **Do not use OpenStax** — its
   licence forbids ingestion by AI systems. When sources disagree, log both and say on the page what both support.
2. **Cite sources** on the page (footer) and in the subject's `DATA-SOURCES.md`. The footer is for students: a short
   "Based on:" line with the textbooks, and a "Models used:" line for simplifications and 3D-model credits. Verification
   notes, URLs and corrections go in `DATA-SOURCES.md` only.
3. If sources disagree, use the more authoritative or more recent one, and say so on the page if it matters for the exam.
4. If something can't be verified, **leave it out**.
5. **Label approximations**: schematic areas, simplified models, hand-placed points ("approximate", "schematic, not to scale").
6. **Guidelines carry a date.** Drug doses, schedules, programme targets and classifications that change: name the
   guideline and its year on the page.
7. **No extrapolation.** Don't claim more than the source says.

## Design rule: graphics first

- Every idea is built as something the student can manipulate; the text is a caption on what is visible.
- Clean and minimal: flat colours, plenty of space, motion only when the motion is the idea.
- Light on resources: a page should load quickly on a phone on mobile data.
- The Revision Hub (`source/`) is raw material, not a script: rebuild its ideas visually and re-verify every fact.

## Visual rules

- Light theme by default (whatever the device setting); dark theme only when the reader picks it with the switch on the
  home page or the Anatomy page. The choice is saved in `localStorage` (`neetpg-theme`) and every page applies it with
  a one-line script in `<head>`; dark tokens live under `:root[data-theme="dark"]`. Usable at phone width (~400 px)
  with no sideways scroll.
- Phones first: the model takes most of the screen; frequent actions (selection card with Open, region/view chips in
  one swipeable row) are visible without scrolling. Tap selects, a second tap (or Open) opens the detailed page.
- Fonts: Bricolage Grotesque (headings), IBM Plex Sans (body), IBM Plex Mono (data), from Google Fonts.

## Technical rules

- No build step for the reader, no framework. External resources: Google Fonts only.
- Non-anatomy modules: one self-contained HTML file each. **Anatomy** pages share `anatomy/assets/viewer.js` (WebGL
  viewer) and `anatomy/assets/atlas.css`, and load model files from `anatomy/models/<group>/` (the femur page is still
  the older self-contained version).
- Every module starts with `<nav class="back"><a href="../index.html">← <Subject></a></nav>` (adjust `../` to depth).
- Relative links only (works on GitHub Pages and locally).
- Keep data (facts, attachments, quiz items) in clearly marked arrays near the top of the script.
- Nothing gives away a predict-then-reveal answer before the reveal. Quiz options are shown in shuffled order.
- `localStorage` only for small conveniences, wrapped in try/catch, with a key unique to the module.

### 3D models

- Bones come from **BodyParts3D** (© The Database Center for Life Science). The OBJ files state CC BY-SA 2.1 Japan; the
  2025 README says CC BY 4.0 — follow the stricter one: credit it in the footer; the simplified meshes we publish are
  under the same licence. Archives live in `sources-local/bp3d/` (not in git): 3.0 at 95 % reduction for detailed
  pages; the whole-body overview (`models/skeleton`) is also built from 3.0 (at 0.6 mm), so the Z-Anatomy muscles,
  which match 3.0, sit on it (4.0 places bones up to ~20 mm differently).
- `tools/bones-rs` (Rust; `cargo build --release`, binary `target/release/bones`): `bones build configs/<group>.json`
  reads the OBJs from the zips, welds, simplifies to an absolute error (mm), writes `NPM1` binaries + a manifest with
  bounding boxes and the **contacts** between parts (sutures, joints). Coordinates stay in the BodyParts3D body frame
  (mm; +x left, +y posterior, +z up), so separately built groups assemble without transforms.
- **Muscles, ligaments, fasciae** come from **Z-Anatomy** (CC BY-SA 4.0, built on BodyParts3D; credit both). See
  `tools/zanat/README.md`: `export.py` reads its `.blend` without Blender and writes the meshes, moved into the
  BodyParts3D 3.0 frame by one fitted transform (`z-to-bp3d.json`: Z-Anatomy = BodyParts3D × 1.0327, shifted ~98 mm),
  as OBJs in `sources-local/zanat/z-bp3d.zip`, so `bones build` uses them like BodyParts3D parts. Bones stay
  BodyParts3D. Config options for mixed builds: per-part `group` + `contacts_across_groups_only` (bone–muscle contacts
  only), per-part `error_mm`, `source` (manifest credit). Z-Anatomy's own origin/insertion patches are hand-drawn and
  sometimes wrong: don't use them. Attachment areas: `tools/zanat/areas.py` (bone vertices near the muscle **and** near
  the landmark the textbook names; proximity alone marks places a muscle only slides over). Check each in a screenshot
  (`tools/test/muscle-dev.html`).
- This machine flips single bits in RAM (suspected faulty memory). In Nov 2026 the cached (in-RAM) copy of the
  BodyParts3D 3.0 zip had 60 bad entries while the copy on disk was intact (`dd iflag=direct` reads past the cache).
  Run `unzip -tq` on an archive before a build; if it fails, compare `sha256sum` with a `dd iflag=direct` read and
  replace the file with the direct copy. Re-hash tracked files against git (`git hash-object` vs the index) and run
  `git fsck` before pushing.
- **Smoothness** (the whole body has ~600 parts with the muscles): models shown on the Anatomy home are built with
  `"pack": true` (one `<name>.pack` file, one request); the viewer uploads each load's parts into shared buffers (one
  draw call per part, or per run of same-coloured neighbours), resolves colours once, and picks by rendering only the tapped pixel. The muscle layer loads
  only when the Muscular system is switched on. Left muscles are not downloaded: the page mirrors the right ones
  (`tools/zanat/body_muscles.py`). Keep new layers to the same pattern. The heart and vessels layer
  (`tools/zanat/export_curves.py` + `body_vessels.py`) and the nerves layer (`body_nerves.py`) work the same way; the viewer draws neighbouring parts of one
  colour with a single call, so order a layer's parts by colour.
- **Moving joints**: `AtlasViewer.setTransform(key, m, t)` moves a part rigidly (`AtlasViewer.rotation(axis, deg, pivot)`),
  `setLines` draws an axis. `tools/joints/general_config.py` (model of the example joints) and `general_axes.py`
  (pivots fitted to the joint surfaces: sphere for a head, circle for a trochlea or condyle outline; the joint space is
  empty because cartilage is not modelled, so surfaces are picked relative to the narrowest gap) ->
  `models/joints-general/motions.json`. Check every movement's direction in screenshots at both ends of its arc.
  Regional joint pages: `tools/joints/ul_config.py` + `ul_axes.py` (shared fitting helpers in `fitlib.py`); ligaments and
  capsules exported with their Blender modifiers applied (`tools/zanat/export_mod.py`, see its README section).
- `tools/bones/skull_points.py`: named sutures and points from the contacts. `tools/bones/assign_colours.py`: bone
  colours. The femur page still uses `tools/bones/build_femur.py` + `embed.py`.
- Python scripts run with the venv `~/personal/buildenv` (numpy, pillow, selenium; run with `python -I`). Page tests:
  `tools/test/ffshot.py URL out.png [--phone] [--wait expr] [--js …]` — headless Firefox forced onto **software**
  rendering (Mesa llvmpipe; it prints the renderer to confirm). Never test on the GPU: the AMD iGPU driver faulted
  under browser rendering on this machine. Pages that fetch models need a local http server
  (`python3 -m http.server 8765 --bind 127.0.0.1` in the repo root). That server does not gzip but GitHub Pages does (so `Content-Length` is the compressed size): after a change to how models are downloaded, also load the live page once it is deployed. (Older tools in `tools/test/` use Playwright.)
- Every computed point or line (landmark, suture, fossa) is checked by eye in a screenshot before it ships, and is
  labelled approximate. If a rule can't place something reliably (e.g. the inion), leave it out.
- Hand-placed landmarks: `tools/test/bone_views.py` (with `tools/test/bone-dev.html`) renders a bone from any direction
  with a pixel grid (`views`), turns chosen pixels into surface points (`pick`, or `aim` at a 3D point; holes get a
  fixed centre from points on their rim) and draws all markers for checking (`all`). One JSON per bone in
  `tools/bones/landmarks/`; `build.py` writes `anatomy/models/skull-detail/landmarks.json`. Place each point from the
  textbook's words ("about 3 cm above the supraorbital margin"), then check it in several views. Spine:
  `tools/spine/landmarks/` -> `anatomy/models/spine-detail/landmarks.json` (`build.py <src> <dst>`; `MANIFEST=` env for
  bone_views.py). Picking inside a canal from above sees through it; compute such centres from the mesh instead.
  Same for `tools/{thorax,upper-limb,lower-limb}/landmarks/` -> `anatomy/models/<group>-detail/landmarks.json`.
  `COLOUR=1` gives each listed part its own colour (to tell small bones apart). Joint facets are easier computed than
  picked: `tools/lower-limb/near.py <manifest> A B mm [z cuts]` prints the centroid of the part of A within mm of B;
  `dorsal.py` gives the top-surface point of each named bone.
- Detailed single bones: `configs/skull-detail.json` (error 0.04 mm, about the source detail); a bone page shows the
  detailed bone over the lighter assembled model (`AtlasViewer.loadPart`).

### Colour

- **One meaning per colour, everywhere** (tokens in `atlas.css`): `--bone`, `--suture`, `--mark` (selected point),
  `--ori` / `--ins` / `--lig` (muscle origin, insertion, ligament — Okabe–Ito, colour-blind safe), `--cart` / `--centre` /
  `--plate` (cartilage, secondary ossification centre, growth plate), `--artery` / `--vein` / `--heart`, `--nerve` / `--dura`. Never reuse a meaning colour for something else.
- Bone identity colours (assembled regions): Paul Tol's "light" palette, assigned by `assign_colours.py` so that bones
  that touch never share a colour (copied to `anatomy/models/skull/colours.json` for the bone pages); bones are also **named on the model**, so nothing depends on colour alone.
- Selecting a part shows the rest as faint glass, so deep parts (sphenoid, ethmoid) are visible whole.
- Check both themes, and that labels stay readable on every bone colour.

## Adding a module

1. List its NMC competencies. 2. Verify every fact; record the sources in `<subject>/DATA-SOURCES.md`.
3. Build `<subject>/<branch>/<name>.html` from an existing module. 4. Add a row to `<subject>/index.html` and update the
subject's line in the root `index.html`. 5. Check light/dark, phone width, no console errors. 6. Tick the SYLLABUS.
7. Commit and push (GitHub Pages updates automatically).
